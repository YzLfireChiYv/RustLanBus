# Windows audio wiring lab

This explicit-device diagnostic entry point connects variable-sized WASAPI capture packets to the new peer protocol and bounded direct-rate playback. It does not change default devices, device volume, mute, application routing, or install a driver. It is a development tool in the Windows integration stage.

    cargo run -p rustlanbus-audio-lab -- devices
    cargo run -p rustlanbus-audio-lab -- probe --source SOURCE_INDEX --output OUTPUT_INDEX
    cargo run -p rustlanbus-audio-lab -- loopback --source SOURCE_INDEX --output OUTPUT_INDEX --seconds 10

Use the indexes from the current devices list. Output is an active render endpoint. Source is either an active render endpoint for system loopback or an explicitly selected capture endpoint, such as a virtual cable's recording endpoint. The source and output must differ. Applications must already send their original sound into the virtual source. Selecting a physical microphone explicitly will capture that microphone. Source muting and system routing remain externally configured in this slice. The probe opens streams without starting capture or playback; loopback starts both for the explicitly requested duration.

The loopback runs two independent peer identities over actual local UDP sockets. Only original capture enters the publication path. Decoded returning audio enters only the remote playback queue. The default `--play remote` keeps original local monitoring off. Choose `--play local`, `--play mix`, or `--play mute` to inspect the independent source branches. This self-loop has no external member, discovery service, router, or persisted permissions. The device-free peer lab remains the saved-intent diagnostic.

The first wiring slice accepts native 48 kHz stereo F32 endpoints and rejects implicit Windows conversion. Other formats need a generalized native-format capture contract. Input and output worker threads retain their own COM apartment and MMCSS registration. Their buffer pools, channels and scratch storage are constructed before stream start. Raw packets retain their source frame positions; they bypass the legacy 480-frame capture reblocker. Encoding and UDP operations run outside the audio workers.

Each playout source uses a prepared ring and independent source epoch, frame cursor, actual arrival-age and backlog policy. The default diagnostic target is two reported render periods; `--buffer-periods 1..8` selects that policy explicitly. Maximum backlog is four target windows within an 8,192-frame capacity, and freshness timeout is 100 ms. At each event the worker submits at most one render period, so a fully empty device buffer cannot retire future source frames. A one-period target can underrun when capture and render events have different phases. Actual capture age is checked in the WASAPI QPC 100 ns domain; coordinator queue age remains included at render ingestion. These policy values are experimental bounds; they are not measured audible latency or the final product minimum. Network/control polling uses a 1 ms wait and allocating diagnostic codec APIs. The bounded standard channels use non-waiting operations and are not claimed to be lock-free.

Unity selection copies finite PCM exactly, including signed zero and subnormal values. Mixing uses explicit gains, defaults to unity per source, and reports samples above unity; there is no hidden limiter. For the self-loop mix of two copies of the same source, choose `--local-gain 0.5 --remote-gain 0.5` if desired. Floating-point mix overflow stops output rather than publishing non-finite PCM. Device processing and physical output remain outside that bit-preservation claim.

Independent-device clock drift is not corrected here. This direct-rate lab may underrun or jump over excess backlog during prolonged playback. Qualified per-source rate correction, fade recovery, hotplug/reopen, the administrator application boundary, virtual-device provisioning and the real participant UI remain Stage 2 work. Re-running restarts the lab; no automatic device recovery or finished product is claimed.
